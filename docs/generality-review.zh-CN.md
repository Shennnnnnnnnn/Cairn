# 通用性边界核查

当前实现的定位是：**由宿主执行、以持久黑板保存目标和事实、支持验收与会话恢复的通用 harness**。模型、工具、权限及并发由 Pi / Codex / Claude / MCP 宿主提供。Cairn 的通用性不等于模型在所有领域都可靠，也不等于自带原项目完整的 Dispatcher / Worker 调度层。

核查入口：

| 边界 | 当前实现 | 意义 |
|---|---|---|
| 宿主 API | `src/harness.ts:createHarness` 只接数据库、会话与引擎选项 | 接入无需指定排障平台或指标结构 |
| 公共工具 | `src/tools.ts` 的 start/read/checkpoint/resume/finish | 面向目标、条件、事实、文件和交接；默认 general + curated |
| 核心状态 | `src/core/types.ts` 的 Task / Claim / Criterion / Artifact / Handoff | 字段不要求根因对象、日志或指标；图表达事实依赖与探索进展 |
| 原生执行 | curated 模式不代理/记录每次原生工具，不设置调用配额 | 编程、文件处理、研究等继续使用宿主工具 |
| 交付验收 | 宿主提供 CompletionVerifier 和 required artifacts | 可验代码测试、结构化数据或其他任务合同 |
| 领域特化 | rootCause / impact / solution 只是可选报告字段 | 仅 emergency 模式将平台证据、因果层级和回执设为强制要求 |
| 多会话 | 保存事实、源文件版本、开放问题、所有者/epoch及交接 | 解决跨会话状态继承，不要求任务属于排障 |

对 `src/` 和 `skills/` 检索三道题的对象、时间戳、题号、AIOps、disk_io及本次模型名称，没有匹配。排障题、隐藏标签和数值验收器属于 `evaluations/public-rca/` 的评测适配层。检索结果只覆盖这些具体标记，不是“所有可能硬编码均不存在”的形式证明。

原项目 `Cairn-main/README.md` 将自身定义为通用问题求解引擎，以 origin→goal、Fact / Intent / Hint 黑板以及从状态图生成探索方向为核心；安全竞赛是其验证领域。当前实现保留目标、事实/假设、提示、依赖图、先直接探索及增量保存等思想，并将执行交还宿主。Round11 冻结实现尚无自动调度。后续新增可选 `Scheduler` / `cairn run`，通过宿主回调实现 Bootstrap / Reason / Explore、提案审核与完成验收；默认五工具插件不自动开启。它没有复制原版的独立服务和全部进程监督能力，见 [调度层指南](scheduler.zh-CN.md)。

冻结前完整回归291/291通过；含运行期间另行提交改动的当前工作区完整检查为294/294，其中包含五工具工作流、跨宿主恢复、原生工具不受接管、产物版本与完成验收。Round11 另以两道不含故障定位要求的真实模型任务验证接入：整数最大余数法代码修复、混合单位/时区/缺测数据整理。五种模型各跑一次，结果单列，见[五模型最终报告](../evaluations/public-rca/comparison-round11.zh-CN.md)；两个合成样例只能支持这两类使用路径，不能证明任意领域成功率。

这十次运行的产物合同检查10/10通过，原冻结运行的Cairn完成状态为9/10。Step算法任务的新增评测验收器未读取stdin，大快照触发EPIPE，因此保留挂起；对全部十份快照只增加stdin读取后复验10/10通过，未重跑模型或改写原状态。这同时说明接入层需要正确实现验收协议，文件内容合格与任务完成不能混作一个指标。

合同检查也不等于报告全文正确：Step算法报告把非整除用例描述成整除，数据报告有一处UTC先后叙述与自己表格不一致。验收范围应明确到行为、数字、文件或结论中的哪一层，不应把通过某层检查外推为全部正确。本轮90次模型比较使用独立冻结实现；运行中工作区另行提交的544597f完成校验/过期验收导出修复未纳入模型复测，版本边界见最终报告。

值得持续改进的是领域覆盖与使用说明：增加开放式研究、文档交付和跨会话的独立验收样例；保持通用入口简短，把领域方法放到可选参考中。事实的 supported 状态来自作者声明；独立验收与独立结论审查的范围需要宿主明确指定。

CLI 的 `submit` 已能在不调用模型时保存目标、条件、约束和初始交接，返回 `executionMode: host-managed`；`serve` 提供本地仪表盘，实际执行仍由宿主接管。它与原版先创建项目、再启动 worker 的顺序相容，但本轮采用的是模型调用 `cairn_start` 的插件路径。GLM 一例在 start 后断线，仍保存初始交接但尚无事实；另一些在首轮请求就失败，根本没有任务。这是启动阶段/未保存增量的区别，不能统称为黑板上下文丢失。默认接入若改为宿主预提交，可以让启动失败也有可观测的任务记录；不需要新模型工作者。

通用体验仍有可收窄之处：公共 checkpoint schema 会展示可选的 rootCause/impact/solution 字段，默认技能也积累了较多因果、时序、单位与缺测指导。它们没有成为 general 模式的领域必填项，但默认说明偏向调查和量化分析。后续可以让 general 模型界面只展示通用字段，将具体方法移到按需参考；默认目标应描述可观测交付及不确定性，而非要求穷尽证明。本轮没有修改这些指令，也没有相关A/B，不能把观察到的耗时差异直接归因于这项候选改动。
