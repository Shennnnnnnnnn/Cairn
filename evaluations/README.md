These six labelled cases are authored fixtures, not competition questions or answers. They cover dependency symptoms, silent data errors, trigger/amplification, healthy distractors, population impact and insufficient evidence.

To evaluate a model, expose only a case's `symptom` and its `observations` through controlled fixture tools. Keep `expected` out of model context. Require a Cairn report and original tool references. Use identical model, tool outputs, deadline and query budget when comparing architectures; evaluate model upgrades separately.

Grade each saved report against the withheld reference:

- Root cause: correct mechanism and causal depth, or explicit inconclusive status when evidence is insufficient.
- Evidence: all required sources were actually queried, references are valid, and cited results support the stated conclusions.
- False positives: no healthy component is labelled faulty.
- Impact: sample versus population is distinguished, with no unsupported expansion.
- Solution: mitigation, root fix and prevention address the observed mechanism.
- Efficiency: correct completed cases, wall time, calls and repeated queries; report partial/inconclusive cases separately.

The infrastructure suite does not establish model diagnostic accuracy. These cases are a reproducible evaluation input and grading rubric; they have not been presented as a measured model benchmark.

## Public AIOps 2022 comparison — 2026-10-16

Four fault instances from one public AIOps 2022 day/testbed were run through real Pi and Pi+Cairn, eight episodes in total. The [protocol and reproduction scripts](public-rca/README.zh-CN.md) and [final comparison](public-rca/comparison.zh-CN.md) retain the source hashes, frozen scoring, a transparent service-identifier review, usage lower bounds, a timeout and independent content checks. Top-1 object plus fault-family matches were 3/4 for Pi and 2/4 for Pi+Cairn; reviewed object-only matches were 3/4 and 4/4. All four Cairn task snapshots passed structural evaluation, including one wrong fault family and one unknown classification. These are metric-only, single-sample exploratory results, not an official competition score.


## Same-case rerun after general harness changes — 2026-10-16–17

The [round-two comparison](public-rca/comparison-round2.zh-CN.md) reruns all eight episodes with frozen code, the same four inputs, model, prompts, scoring policy and 720-second limit. Cairn adds compact receipts, aligned checkpoint validation, an optional host output-contract verifier and a 90-second submission reserve. Reviewed object/family joint matches remain 2/4 for Cairn, versus 4/4 for the fresh Pi control. Missing-summary errors fall from 20 to 0, while Cairn timeouts increase from one to two. The two verified completed tasks both misclassify the fault family; the two joint-correct answers remain active at timeout. All eight outputs received fresh numerical reviews; record checks pass 54/54 and implementation/configuration checks 66/66. These engineering improvements do not establish better diagnostic accuracy or reliable deadline completion.


## Artifact acceptance and layered handoffs — 2026-10-17

The [third public-case comparison](public-rca/comparison-round3.zh-CN.md) records eight new frozen main episodes, one fresh-session Pi delivery recovery and four offline reload checks on copies of real Cairn databases. Cairn completed 4/4 and passed the artifact contract plus independent CSV arithmetic replay in 4/4, while root-object-plus-family accuracy remained 2/4 and object accuracy was 3/4. Two semantically wrong completions remained. Pi saved 4/4 correct diagnoses, with one output-budget stop before its report was written; recovery completed that delivery in 142.78 seconds and 83480 additional tokens. No Cairn natural recovery sample occurred, so the 4/4 database-copy checks do not establish a model recovery rate. New checks.json requirements, single samples, interrupted usage lower bounds and prompt-only filesystem boundaries limit historical and cost comparisons.
