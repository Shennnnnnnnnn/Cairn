# 公开 AIOps 2022 排障案例对照与最终结论

实测日期：2026-10-16。基于提交 `8747c942e73645397603154dfca06c6b68e55bfa`，Pi 1.1.0，API 配置模型 `sub2api-copy-copy/kimi-k3`，thinking=high。模型名称为服务端返回标签，未独立验证底层模型身份。


## 最终判断与工程方向

**保留 Cairn，定位为可选的通用任务状态、证据与验收层；当前证据不足以把它作为提高排障准确率、缩短耗时或节省 token 的默认方案。** 本轮最明确的收益是可检查的持久化状态。最明确的问题是工具调用摩擦和语义验收缺口，应该先修这两项，再扩大推理框架。

四组真实比赛指标切片中，Pi 的第一候选对象与资源大类联合命中 3/4，Cairn 为 2/4。Cairn 的第一候选对象经服务标识符复核全部命中，资源大类只命中两组。内存题明确误判为 disk_io；网络题选择 unknown，应理解为保留判断。Pi 的报告也存在单位换算、历史峰值恢复判据和数字引用错误，标签命中不能直接等同于报告可靠。单组、单次结果不能证明 Cairn 导致了误判，也不能支持普遍能力提升。

四个 Cairn 任务都保存为 completed，独立 SDK 结构评估全部通过；其中仍有内存类别错误和网络类别未判定。其验收验证的是声明、覆盖和引用的结构，尚未独立验证声明是否正确。部分任务把四项交付要求压成一个宽泛标准，状态完整度因此比业务正确度更容易达标。I/O 题的四条 Finding 与五条依赖在最后一次 finish 一起提交，证明了原版黑板/DAG 思想可以保留，但本轮没有证明 DAG 指导了中间探索、减少了重复工作。

对应最初三个目标：通用 harness 的轻量 SDK、五个生命周期工具和宿主适配边界值得保留；原版的证据黑板、依赖、历史和反馈重开应继续作为核心语义；接入体验则尚未达到可默认启用的程度。本轮四次 Cairn 运行共触发 20 次缺 summary 的 checkpoint 错误，且无模型复现器确认了 schema 允许省略、普通 checkpoint 运行时却必需的契约分歧。这是已经验证的接入摩擦，而不是模型能力的猜测。

下一轮优先做三件事：

1. **修正交互契约与控制开销**：普通 checkpoint 条件性要求 summary，分支 heartbeat/release 保留必要例外；提供最短合法示例，连续同类错误及时返回可执行纠正信息，限制状态回传体积。
2. **加入外部语义验证与反证覆盖**：由确定性计算、领域规则或独立审阅验证关键数值和单位；关键反证必须解释。验证失败应产生结构化反馈并重开相关结论，不能仅凭模型自标 supported 完成。让 answer、量化证据、替代解释与一致性成为可分别验收的标准。
3. **接通宿主预算与收尾机制**：将剩余时间/输出额度传到执行与 checkpoint，预留保存、结论和退出时间；把“文件已保存”“任务 completed”“宿主正常 stop”作为三个不同的可观测状态。此次 720 秒限制由外部 runner 强制实施，未传入 Cairn，不能据此判定其内部 deadline 握手失效。

前轮两个人工案例中，代码修复两组都通过 27 项独立验收，Cairn 那一例更快；两阶段排障的 Cairn 复核则超时，文件与任务状态不一致。本轮增加公开比赛实例后，仍然没有得到稳定的提速、节省 token 或诊断质量收益。两个实验轮次的任务性质和日志实现不同，不将延时简单合并成一个总体性能比率，详见 [前轮报告](../pi-ab/comparison.zh-CN.md)。

工程上建议先用于需要留痕、交接、复核和反馈重开的较长任务，作为可选择启用的一层。默认短任务是否值得接入，应在修复契约后，用不同测试床、不同日期与重复采样继续验证。本轮没有主动制造原生上下文丢失，也没有检验多 worker 租约或跨宿主接管，不能将持久化状态的存在写成恢复能力已经全面胜出的结论。

## 来源、输入与公平性

来源链为 RCLAgent 作者公开的 AIOps 2022 数据说明 → Zenodo 归档 19176851 → training_data_with_faults.zip。`2022-03-20-cloudbed2` 的标签文件按 timestamp 排序取前四行，在模型运行前固定。四例来自同一天、同一测试床，不能当作四个独立平台。镜像发布者说明原始入口已不可用，本轮使用其第三方归档；镜像声明的许可信息记录在 provenance.json，原始数据不随仓库再分发。

每题仅保留故障标签时刻前后各 600 秒的全部 container/node/service 指标原始行，57 个 CSV、约 5.8 万行；未筛选故障对象、未合成指标、未提供答案。模型获得故障时刻，不需要从全天发现告警。没有提供日志、调用链、拓扑、指标类型元数据与在线系统。原始标签、镜像路径及独立评分器均在模型工作区之外。case-02 的前段仍含前一事件的尾部，保留了这种原始混杂。

同一模型、高思考、maxTokens=8192/回复、完整回复输出上限 24000；单并发、交替先后顺序；全新工作区与原生会话。两组相同任务、证据、交付格式与时间上限，Cairn 额外加载扩展/skill 并要求 start/checkpoint/finish。Pi 基线可用脚本与文件记录。此处测试的是实际使用 Cairn 协议的额外收益与开销。目录访问依赖指令约束，无操作系统隔离，不能排除训练数据污染。

原始自动评分在运行前冻结：对象精确匹配（允许 node 前缀规范化）、资源大类 CPU/memory/disk_io/network、Top-3/MRR；网络损坏/丢包/延迟等细分不从有限指标强行判别。本轮分数是自定义离线诊断分数，不等同官方比赛成绩。在查看网络题两组答案前补充标识符复核：service 的 -grpc/-http 后缀与无协议后缀标签视为同一服务；仅此拼写差异可归一，不把一个 pod 自动升级为整项 service 命中。原始评分完整保留，表中同时列出复核结果，依据见 identifier-policy.json。每组每题一次，无统计显著性或稳定加速结论。前轮采用不同任务与分阶段预算，两个实验轮次不直接汇总速度比。

## 逐例语义复核

主评分只衡量标签命中；以下是独立内容复核，不追加一套事后百分制。

- **写 I/O / Pi**：目标 pod 和类别正确，节点 I/O 利用率、写等待和服务延迟三个关键数值复算一致。报告把非单调写入序列的正差分称为实际写入量“下界”，缺少计数语义依据；平均 I/O 利用率 15.6%、峰值约 30.9% 也不能单独证明“饱和”。另有一个 7 秒的时间区间表述错误、容器覆盖数写错。
- **写 I/O / Pi+Cairn**：目标和类别正确，原始写盘峰值和磁盘占用确有突变；明确保留了节点/容器层级和写盘细分类别的不确定性。将原始序列认定为“已核实的 60 秒差分值”，据此换算 MB/s 与 24.7GB 总写入，证据不足；保存的 analyze.py 仍按累计值做差分，且混合了不同 kpi_name 序列，和报告的说明不完全一致。10 次 checkpoint 缺 summary、2 次 finish 缺覆盖后，才在最后一次 finish 提交四条 supported Finding 和五条依赖；这些是实际持久化的模型声明，不是内容真实性的裁判。原始四项交付要求被压成一个宽泛 c1，验收粒度也偏粗。
- **节点 CPU / Pi**：node-6 与 CPU 类别正确，50.19/49.70/49.54 三个峰值点吻合，较好地把窗口前的内存/IO 遗留异常与当前 CPU 峰值分开。将容器样本解释为 core 并据此认定故障进程在监控 pod 外，缺少核数和采集口径支持；后文又保留了“pod 指标漏采”的替代解释。一次连接错误后恢复，最终正常 stop，故不能把其视为全过程没有网络异常。
- **节点 CPU / Pi+Cairn**：对象和类别正确，三个 CPU 峰值点复算通过；同样存在用容器 core 与节点百分比比较、推断进程在 pod 外的证据跳跃。报告和答案已写入、Cairn 也 completed，但后续模型进程触及 720 秒上限；因此“保存完成”和“进程正常结束”在此例不同。中途有两条模型错误响应并恢复了后续执行，不能将全部用时归因于协议开销。
- **容器内存 / Pi**：pod 与 memory 大类正确，max_usage 到达 128MB、failcnt 增长等主要信号属实。但声称“没有独立 spec_memory_limit_MB”与输入矛盾：对应文件有目标 pod 的 20 行，全部 128MB。将历史 max_usage 回落当作通用恢复判据不成立，除非明确考虑重置/重启；历史峰值保持不等于当前仍在触限。RSS 峰值时间写成不存在的 1647738975（实际 1647738960），failcnt 末值 56894（实际 56889）、均值速率 92.4/s（按报告窗口复算为 89.2742/s）也有误；adservice 的 sr 并非报告所称 100%。这些问题不改变标签命中分，却影响报告可信度。
- **容器内存 / Pi+Cairn**：pod 正确，类别错误：首选 disk_io，其后 cpu、节点 disk_io，未把标签中的 memory 列为候选。磁盘读原始样本合计、节点读尖峰确有变化，但最终报告没有解释已提供的内存 max_usage=128、独立 limit=128、failcnt 从 0 增至 56889；详细目标脚本只检查 usage/working_set，没有纳入这些关键反证。其 CPU 换算比 Pi 明确：9.31 CPU-s/60s≈0.155 core，而非 9.31 core；也正确保留了 adservice 低 sr 基线。任务最终 completed，6 条 Finding（5 条 supported、1 条 proposed）、3 条依赖、3 项标准覆盖，SDK evaluateTask.ok=true，外部标签判定却为错误。此例直接说明结构校验与语义裁判的边界。
- **服务网络 / Pi+Cairn**：首选 `productcatalogservice-grpc` 与无协议后缀标签指向同一服务，位置复核计命中；类别保留 unknown，因此 network 不计命中。这里属于保留判断，和内存题明确误判 disk_io 应区分。6 个连续缺失采样点、930.3→216 的完成量下降、延迟峰值 4827.89ms 均有原始数据，最终脚本独立重跑成功。报告明确区分调用拓扑推断与实测，合理保留缺数原因不确定性；但“不是网络丢包”的措辞过强，监控计数器为零不能排除标签所示的网络损坏。CPU 样本直接写成 core 仍缺采集口径。8 次缺 summary 的错误、1 次随后修复的脚本错误和一次恢复后的连接错误均保留。
- **服务网络 / Pi**：network 类别正确，首选位置 node-5 与标签不同，正确服务 `productcatalogservice-grpc` 排在第三；依据在网络答案揭示前记录的协议后缀等价政策，Top-3 对象计命中。TCP 重传 0.01→1.35375、UDP 错误 0.003→0.52125、数据报 46.662→7.3425，以及 frontend 延迟峰值 38410.16ms、最低 sr=40% 均独立复算通过，最终分析脚本重跑成功。报告诚实保留节点/pod 与损坏/丢包/延迟的不确定性；但错误绝对量更大不能单独证明 node-5 是根因，它本就覆盖 35 个容器，node-6 为 7 个；容器计数为零也不能排除比赛所标注的容器网络损坏。一次模型请求超时后恢复并正常 stop，不是实验进程超时；token 按记录下界计算。
