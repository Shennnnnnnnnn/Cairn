# Round14：Pi Kimi K3 原生与 Cairn 对照

本轮仅换模型，框架 src/dist/skills 与 Round13 完全一致。用户确认的模型显示名为 `sub2api-kimi`，实际配置键为 `sub2api-copy-copy`，模型 ID `kimi-k3`，两组均 high。没有改写模型注册或用户全局配置。

**最终结论：本轮 Kimi 两组均正确 6/9、完成 9/9、错误完成 3/9。Cairn 改善了交付一致性和部分用量，未改善根因层级判断。** CPU、内存题两组均 3/3；I/O 题两组均 0/3，全部识别了 shippingservice 四副本同步异常，却以“代表 pod”作为第一候选，失配服务级注入标签。这不是 `disk_io` 类别判错。

## 错误与验收问题的直接原因

两组流程未完成均为 0。两次原生 `Connection error.` 均由 Pi 自身重试后正常结束：new-03-r1 与 new-01-r3，不能记成 Cairn 恢复。

| 样本 | 结果与直接问题 |
|---|---|
| new-01 全部六次 | 第一候选均为 shippingservice 的代表 pod，隐藏标签是 service shippingservice；资源家族 disk_io 全部匹配。服务在部分候选中已列出，合同也能表示 service；主要是模型的范围选择与完成自审没有纠正代表对象替代根因对象。 |
| native new-01-r1 / r2 | 磁盘 KPI 校验漏掉 `/dev/vda`、`/dev/vda1` 等实际设备后缀，独立验收找不到对应样本；其余产物齐全。 |
| native new-02-r2 | checks 与 answer.evidence 对应实体不同，根因正确但交付未通过；因此正确6/9而有效交付5/9。 |

报告已明确写出四副本同步异常、且某些报告把正确的 service 放在低排名；因此“关键事实完全丢失”不是这些错误的充分解释。更直接的公开证据是：模型把“需要单一 location”解释成“必须选一个代表 pod”，没有保持影响面与结论层级的一致。没有提示词 A/B、未见任务集或强制复核消融，不能唯一断定首轮提示、模型偏好或自审策略各自的因果占比。

## 报告语义复核

独立算术验收只确认所声明的数值和选择器，不认证全文的时序、单位、采集口径与因果解释。对评分前阅读笔记做了七项原始 CSV 定向复核；[完整复核证据](runs/2026-10-18-kimi-scheduler-round14/report-quality-review.json) 保存封存报告 hash、行号、原句、源 CSV hash、选择器和完整原始点列。

| 问题 | 可核实证据 |
|---|---|
| working set 与总内存混用 | I/O r1/r3 Cairn 用“远低于 limit”排除内存压力；原始 total usage 峰值255.9727MB、limit256MB，较小的 working_set 不等于较小的 total usage。r1 还说容器读量全为0，实际设备后缀时序峰值4080.9395。 |
| 首个突变样本错移 | I/O r1 Cairn 把 fs_usage 大跳变写为1647750900；原始该点33.2227MB，到1647750960才为656.1953MB，偏移一个采样。不能据此进一步断言未观测到的真实注入起点。 |
| 单位内部矛盾 | I/O r2 Cairn 将约2.4同时写成“核·秒/60s”和“核”，字面上差60倍。采集语义未说明，不在这里猜定真实单位。 |
| 背景成功率被写成100% | memory r1 native、memory r1/r2 Cairn 有“全部服务 sr=100%”断言；同源 adservice 实为70.8772%–75.4579%。它是既有基线而非新故障，不应改写成健康100%。其他重复中已有正确的基线说明。 |
| 小数不等于非累积 | memory r3 native 因 failcnt 出现1485.5便按 gauge mean 处理；实际0→1485.5→2971仍单调不减。小数不能单独证明累积语义消失，数值重放通过也不证明采集语义正确。 |
| 端点遗漏中间压力 | memory r3 native 据接近的首尾值称 node-5 内存全程平稳；完整 mem.used 范围为8384–9167，存在中间升高。 |

也有正确处理：多数 CPU 报告保留 node-2 缺少容器覆盖这一限制，没有把缺测当成健康；若干内存报告正确区分历史高水位、当前用量与 failcnt 增量，并承认没有 OOM 事件记录。上述定向复核不是对全报告的穷尽评分。

## 成本波动与后续改进方向

- 原生 CPU r2 用1,464,743 tokens、42次工具，REPORT在第41次才写出，写后仅约15.1秒；其成本主要积累在报告前的扫描/重算，不能套用 Round13 DeepSeek“报告后长尾自检”的解释。原生 CPU r3 则用了953.7秒、899,923 tokens、38次工具。
- Cairn CPU r3 共836.3秒、917,677 tokens；首个 REPORT 写出后又用335.9秒、508,911已记录tokens完成合同/DAG修复。这些是有交付效果的返工，依然是成本。
- Cairn原始CLI阶段合计4796.4秒，actor总计4803.6秒，约7.2秒差额包含调度、验收、文件与驱动外围工作；这是墙钟差值而非独立CPU profiling。主要开销仍在模型阶段与续接历史。
- 首轮显式提示为原生325B+C306B common，Cairn3300B+C306B common。四次 Reason/delta 提示为9015/7060/9288/7776B；没有 fresh-vs-resume 消融，不能把总用量下降单独归因于 delta。

后续值得优先验证的是：通用的“证据范围—候选层级—结论”一致性复核；用结构化元数据保留单位、指标身份、窗口和缺测，避免 working_set/usage、基线速率/绝对值互换；减少阶段可选字段或利用宿主已有结构化输出能力，降低正文包裹、next类型与依赖图纠错。它们应保持通用，不以这三个答案设规则。**本轮没有据测试结果修改框架。**
